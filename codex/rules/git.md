# Git 작업 규칙

## 기본 완료 흐름
1. 저장소 루트·원격·브랜치·기존 변경·프로젝트 지침을 확인한다.
2. 기준점을 확인하고 feat/·fix/·refactor/·docs/·chore/ 작업 브랜치를 만든다.
3. 구현 후 프로젝트에 필요한 검증을 실행하고 diff를 검토한다.
4. 자신의 변경 파일만 명시적으로 선택해 커밋한다.
5. 브랜치를 push하고 PR을 작성한다.
6. 필수 검사·승인·병합 조건을 확인하고 저장소의 기본 배포 브랜치(보통 main)에 자동 병합한다.
7. 연결된 자동 배포를 추적하고 서비스 상태까지 확인한다.

- 이미 합의한 계획에서는 커밋·push·PR·병합마다 다시 승인받지 않는다.
- 질문·조사·초안만 요청한 작업에는 이 변경 흐름을 적용하지 않는다.
- 커밋은 Conventional Commits: `feat(editor): 노드 연결 기능 추가` 형식을 기본으로 한다.
- 설명은 한국어 명사형으로 간결하게 쓰고, 복잡한 변경은 본문에 이유와 핵심 내용을 기록한다.
- PR에는 문제와 변경 후 동작, 필요한 검증·제약을 적는다. 대화 기록을 나열하지 않는다.
- 저장소 정책이 없으면 squash merge한다. 기존 보호·필수 승인을 우회하지 않는다.
- 원격 필수 검사가 없어도 변경 위험에 맞는 검증은 생략하지 않는다. 프로젝트 필수 로컬 검사와 관련 기능·운영 영향 확인 결과를 기준으로 병합한다.
- 실패한 검사는 원인을 수정하고 재검증한다. 권한·외부 승인 등 실제 차단은 기록한다.
- 운영 checkout은 배포 브랜치를 유지한다. 작업 브랜치 변경은 개발 checkout/worktree에서 한다.
- 기존 변경 덮어쓰기·임의 stash·강제 push·공개 이력 재작성·무차별 git add를 하지 않는다.
- dirty 상태에서는 자신과 무관한 변경을 별도로 보존하고 커밋에 섞지 않는다.
- 원격이 없으면 임의 공개 저장소를 생성하지 않는다. 로컬 성과와 미완료 이유를 보고한다.
- 자동 배포가 이미 있으면 결과를 추적하고 중복 실행하지 않는다.
- 병합 완료와 배포 성공은 별도로 보고한다. 배포 대기에는 프로젝트의 제한 시간을 적용하고 미확인을 성공으로 보고하지 않는다.
- 새로 필요한 파괴적 변경·공개 확대·비용·중단 시간 초과는 전역 지침의 범위 변경 기준을 따른다. 이미 승인된 병합·배포는 재승인받지 않는다.
