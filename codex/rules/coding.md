# 코드 작업 규칙

## 구현 전에 생각한다
- 가정을 명시한다. 불확실한 점을 숨기지 않는다.
- 여러 해석이 있으면 중요한 차이를 설명한다. 임의로 하나를 고르지 않는다.
- 더 단순한 해결책이 있으면 제안하고, 과도한 요구에는 근거를 들어 이견을 말한다.
- 파일·설정·실행 상태로 확인할 수 있는 사실은 먼저 조사한다.
- 중요한 모호함은 질문한다. 합의한 범위에서 세부 구현마다 재승인받지 않는다.

## 단순성을 우선한다
- 요청한 문제를 해결하는 최소한의 코드만 작성한다.
- 요청하지 않은 기능·확장성·설정 옵션을 추가하지 않는다.
- 한 번 쓰는 코드에 불필요한 추상화를 만들지 않는다.
- 발생할 수 없는 상황을 위한 오류 처리를 추가하지 않는다.
- 50줄로 해결할 일을 200줄로 작성했다면 단순화한다.
- 숙련된 개발자가 과도하다고 느낄 설계인지 점검한다.

## 필요한 부분만 수정한다
- 인접 코드·주석·서식을 함께 개선하지 않는다. 정상 코드를 이유 없이 리팩터링하지 않는다.
- 선호와 달라도 기존 스타일에 맞춘다.
- 기존 죽은 코드는 알리되 요청 없이 지우지 않는다.
- 자신의 변경으로 사용하지 않게 된 import·변수·함수만 정리한다.
- 변경한 각 줄이 사용자 요청과 연결되는지 확인한다.

## 검증 가능한 목표로 실행한다
- 기능 단위로 계획하고 각 단계의 성공 기준과 확인 방법을 정한다.
- 문제 수정은 원인을 확인하고 회귀 위험에 맞게 검증한다.
- TDD 채택 여부는 프로젝트 지침과 설계에서 확인한다. 모든 프로젝트에 강제하지 않는다.
- TDD 프로젝트: 실패 테스트 작성·실패 원인 확인 → 최소 구현 → 통과 확인 → 필요한 리팩터링.
- 테스트는 외부에서 관찰할 동작을 검증한다. 구현을 그대로 복제한 테스트는 피한다.
- 테스트 파일 위치와 도구는 언어·프로젝트 관례를 따른다.
- 비TDD 프로젝트: 변경 위험에 맞게 기존 테스트·타입체크·린트·빌드·실행 검사를 선택한다.
- 사소한 문구·설정 변경까지 새 테스트 작성을 강제하지 않는다. 기존 필수 검사는 통과해야 한다.
- 검증하지 못한 항목과 이유를 보고하고, 확인하지 않은 성공을 주장하지 않는다.
- 화면 검증을 사용자에게 넘기도록 정한 프로젝트의 제한은 존중한다.

## 탐색·주석·의존성
- 수정 전에 실제 대상과 관련 문맥을 읽는다. 필요 없이 파일 전체를 반복해서 읽지 않는다.
- 검색은 rg와 관련 경로를 우선한다. 의존성·빌드 결과·세션 기록을 무차별 탐색하지 않는다.
- 긴 출력은 필요한 부분과 요약으로 줄인다.
- 주석은 간단명료하게 작성하고 코드만으로 명확한 내용은 반복하지 않는다.
- 의존성 추가 전에 공식성·사용 현황·유지보수·라이선스를 확인한다.
- npm 의존성은 필요 시 `npm view <pkg> license`로 확인하고 기술 선택이 바뀌면 DESIGN에 반영한다.
