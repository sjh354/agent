# 과거 샌드박스 서버 참고 자료 — 현재 정책으로 적용 금지

이하 내용은 이전 서버 원문이다. 경로·도메인·권한·백업 보존 기간·검토 시스템은 현재 homeserver에서 확인되지 않았다. 현재 구성이나 실행 지시로 사용하지 않는다.

# 이 서버의 환경·운영 정책

## 적용과 권한
- sjh354.xyz 및 서브도메인을 운영하는 이 서버에서 적용한다. 다른 호스트에 경로를 그대로 적용하지 않는다.
- 이 Codex 세션의 넓은 권한은 사용자가 의도적으로 부여한 무인 운영 권한이다. 권한 축소·승인 단계 추가를 부수 작업으로 수행하지 않는다.
- 권한의 존재와 작업 승인 범위는 구분한다. 승인 범위에서는 비대화형 sudo를 포함한 필요한 작업을 자율 수행한다.
- sudo가 필요하면 먼저 `sudo -n`으로 가능 여부를 확인한다. 비밀번호를 출력·저장하거나 대화형 입력을 기다리지 않는다.

## 경로와 작업 공간
- 인프라 저장소: `/home/user/infra/mainserver`; 운영 checkout·runner·배포 산출물: `/home/user/infra/services`.
- 신규 개발: `/home/user/projects/<repo>`; 병행 작업: `/home/user/worktrees/<repo>/<task>`.
- 폐기 가능한 실험: `/home/user/scratch/<task>`; 영속 데이터: `/mnt/vault/data`.
- `/home/user/data`는 `/mnt/vault/data`의 편의 링크다. 운영 Compose는 실제 데이터 경로를 사용한다.
- 로그: `/home/user/logs`; 백업: `/home/user/backups`; 과거 구성: `/home/user/.legacy`.
- 공통 비밀 설정 원본은 인프라 `.env`, 앱 전용 설정은 해당 앱 `.env`다. 앱이 다른 원본을 사용하면 실제 구현을 확인한다.
- 개발용 DB의 데이터·계정·포트는 운영과 분리한다. 별도 데이터 경로 예: `/mnt/vault/data/db/<project>-dev`.
- 직접 생성하는 서버 작업 디렉터리는 위 구조를 따른다. 앱이 지정한 작업·산출물 경로와 사용자의 기존 경로는 정리 요청 없이 이동·삭제하지 않는다.
- SDK·사용자 도구는 기본적으로 `~/.local/share`를 사용하되 도구의 필수 기본 경로는 존중한다.

## 데이터·배포·백업
- SSD `/mnt/vault`가 마운트되지 않으면 서비스를 시작하거나 빈 데이터 경로를 만들지 않는다.
- Docker systemd의 마운트 의존성, 배포 전 mountpoint 검사, bind의 자동 경로 생성 방지를 유지한다.
- mainserver Compose 프로젝트 `server`, 네트워크 `server_server_net`을 유지한다. 다른 앱은 해당 프로젝트의 명시된 이름을 따른다.
- CI·수동 배포·에이전트가 같은 운영 대상을 동시에 변경하지 않도록 동일한 잠금에 참여하게 한다. 기존 장치의 실제 구현을 먼저 확인한다.
- 빌드·테스트 동시성과 자원 상한은 프로젝트의 실행 도구에서 정하고, 운영 서비스를 관찰해 적용한다. 일괄적인 컨테이너 자원 제한 변경은 별도 작업이다.
- 일반 백업 보존 기간은 7일이다. 이 보존 정책은 DB·설정·에이전트 규칙 백업에 적용하고 서비스 통계·검토 요청·감사 기록의 보존 기간으로 확대 해석하지 않는다.
- 보존 기간 정리는 확인된 백업 전용 경로와 완료된 백업만 대상으로 한다. 새 백업 실패 시 마지막 정상 백업을 지우지 않는다.
- 미해결 작업의 유일한 복구본·이전 원본·보존이 명시된 자료는 기한만으로 삭제하지 않는다. 기존 자료를 소급 일괄 정리하지 않는다.
- 백업 주기·시각·저장 대상과 정리 실행 장치는 실제 설정을 확인한다. 문서의 정책만으로 자동화가 구현됐다고 보고하지 않는다.
- 복구는 자동화하지 않는다. 복구 명령·호환성·선행 조건을 기록하고 복구가 필요하면 작업 승인 범위와 데이터 영향을 확인해 수동으로 실행한다.
- 운영 변경 기록은 `/home/user/logs/admin/changes.log`에 시각·이유·영향·백업·검증·수동 복구 방법을 남긴다.

## 중앙 권한·검토 요청
- 서버 전체의 권한 요청·실행 대기 명령·검토 사항은 `https://admin.sjh354.xyz`를 중앙 저장소로 사용한다.
- 공식 CLI는 `/home/user/.local/bin/adminctl`이며 검증된 current release를 호출한다. 문법은 `adminctl help`와 `~/.codex/skills/adminctl/SKILL.md`를 확인한다.
- 머신 토큰 원본은 `/home/user/.config/adminctl/token`(파일600·디렉터리700)에 둔다. 토큰을 인자·채팅·로그에 넣지 않는다.
- 검토 생성·사전 정의 작업 제출은 고정 idempotency key를 사용한다. 수정은 현재 revision을 포함한다.
- API 장애 시 CLI의 명확한 실패를 보고한다. JSONL·Markdown·별도 파일에 요청을 자동 대기시키거나 자동 재시도하지 않는다.
- 기존 `/home/user/logs/admin/needs-review.jsonl`과 `/home/user/infra/mainserver/docs/needs-review.md`는 출처 식별자로 이관·대조한 원본 이력으로 보존한다. 신규 접수·장애 대기함으로 사용하거나 원본을 삭제하지 않는다.
- 등록 정보에는 프로젝트·kind(permission/review)·제목·맥락·명령(없으면 null)·cwd·필요 권한·이유·시도·위험을 포함한다. 비밀 값 대신 참조할 설정 위치를 적는다.
- 검토 기록과 상태 변경을 명령 실행 승인으로 간주하지 않는다. 임의 셸 명령은 웹의 사람 관리자만 해당 revision을 검토하고 실행한다. 머신 토큰·CLI 상태 변경으로 실행 권한을 얻지 않는다.
- 안전 hook 차단은 운영 권한 대기와 구분한다. 기록이나 관리자 실행기로 안전 차단을 우회하지 않는다.
- 조사·계획만 요청받으면 차단은 대화로 보고하고 파일·API 기록을 변경하지 않는다. 별도로 승인된 기록 작성만 수행한다.
